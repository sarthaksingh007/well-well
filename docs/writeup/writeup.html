Well-Well — Asset Intelligence Copilot

FlytBase AHC SWE Hack Day, Pune · 17 Oct 2026 · open source (MIT) · docker compose up → http://localhost:8765
Design principle. The language model decides what to look up and how to say it; deterministic code decides what is true. Every number in an answer is computed by SQL/Python from the records, and every claim cites the inspection, repair, regulator event, note or manual section it came from.

Data: storage, indexing, retrieval

  • Load: wellwell load <folder> --dataset test upserts on the dataset's own IDs (INS-…, MNT-…), so the test release merges next to the sample; a status endpoint drives a progress dialog (wells x/y, indexing).
  • Rules come from documents, not code: producing threshold (T200 15 °C, T350 20 °C), alarm limit and RCA rule are parsed from each manual; containment hours, spill class and the compliance table from each repair report.
  • One truth view: inspection_facts applies the latest active correction per field and computes margin over air, producing flag and effective spill, for every tool and user.
  • Text search: manuals/SOPs/reports split by heading; BGE-large (bge-large-en-v1.5, local) vectors stored in Postgres keyed by text hash, fused with BM25 by reciprocal rank. Modes: Semantic (default), Smart (hybrid), Exact words.
  • Fallback: read-only SQL for questions no tool covers.

Tools and how sources combine

Typed, parameterised tools (any well, area, type, period, metric). Numbers, documents and notes meet inside them: downtime = 7 days × weekly inspections below the manual threshold, each explained by the repair it triggered or the note covering it; SR-02 compares discovery time with containment hours that exist only in report text; SR-01/SR-03/RC-04 compare regulator events with SOP deadlines.

Memory (two levels)

  • Shared: notes ("WELL-0007 shut in from 17 Oct"), corrections and claims are stored per well or well type with author and reason; every user's later answers include them.
  • Learning from feedback: corrections to raw data or AI analysis keep the original value, who, why, when; a newer one supersedes, both stay. Team rules ("T350: RCA after 2") apply to that type only.
  • Private: conversations and the wells in each answer are per user; recall filters by the signed-in user, so "the wells we discussed yesterday" never reaches another user's history.
  • Self-evolving playbook: each verified answer stores an anonymised question pattern + tool plan; 👍/eval passes raise trust, 👎 marks it to avoid; similar new questions get advisory hints (BGE similarity ≥ 0.82). Kill switch per request.

Conflicts and new data

  • Claims are checked against the latest inspection (confirmed / contradicted → kept as unconfirmed, both sides shown, user asked to confirm). Opinion notes never override data; only formal corrections do. Stale recorded status is flagged.
  • New data: same loader, rules re-read, only new text embedded; tolerant parsing with load warnings; unseen questions use generic tools, aggregate, doc search and SQL.

Models and cost

Gemini 3.5 Flash-Lite (≈1.2 s/call) primary, Gemma 4 26B fallback (both free tier on the Gemini API); BGE-large local on CPU/Apple GPU. 1–3 model calls per question; median answer 4 s. Cost: USD 0.

What worked

  • Deterministic tools made answers exact and repeatable; the model never does arithmetic.
  • Reading thresholds and deadlines from the manuals/SOPs instead of hard-coding them.
  • One corrected view (inspection_facts) made corrections reach every answer and user.
  • Prefetch + a fast model brought typical answers from 40–130 s to 2–10 s.

What didn't, and why

  • The free Gemma endpoint returned frequent 500/504s; fixed with backoff, hedged requests and a model fallback chain.
  • A Postgres NULL-ordering difference picked the wrong downtime cause; found by the eval, fixed with explicit ordering.
  • Private recall initially fell back to an unrelated chat; now it requires a match and otherwise says there is no such conversation.
